### What I did

- Before writing any code, read pdf.js's actual runtime source (`node_modules/pdfjs-dist/build/pdf.worker.mjs`, `node_modules/pdfjs-dist/build/pdf.mjs`) rather than assuming operator-list shapes from memory, since the plan only sketches the approach at a high level. Confirmed: `OPS.paintImageXObject`'s `argsArray` entry is `[objId, w, h]` (the image's own pixel dimensions, not its on-page size — the real placement comes entirely from the current transformation matrix, since pdf.js always paints an image into the unit square (0,0)-(1,1) of whatever coordinate system is active); the `cm` operator (`OPS.transform`) always carries exactly 6 numeric args (`numArgs: 6` in the worker's operator table); and `Util.transform(m1, m2)` / `Util.applyTransform(p, m)` (both exported from the top-level `pdfjs-dist` package, confirmed via `node_modules/pdfjs-dist/types/src/pdf.d.ts`) are pdf.js's own matrix-composition helpers — reusing them instead of hand-deriving the multiplication order avoided a real chance of getting the row-vector convention backwards.
- Verified the composition order empirically before trusting it in real code: worked out by hand that `Util.transform(m1, m2)` produces a matrix equivalent to "apply `m2` first, then `m1`" (confirmed with a simple translate-then-scale example), which matches the PDF `cm` operator's actual semantics (`CTM_new(p) = CTM_old(M_cm(p))`) when called as `Util.transform(currentCTM, cmArgs)`.
- Added `/src/lib/imageRegions.ts`: `getPageImageRegions(doc, pageNumber): Promise<ImageRegion[]>`. Walks `fnArray`/`argsArray` from `page.getOperatorList()`, maintaining a matrix stack via `OPS.save`/`OPS.restore` and updating the current CTM via `OPS.transform`, and at each `OPS.paintImageXObject` maps the unit square's four corners through the current CTM (`Util.applyTransform`, which mutates its point argument in place rather than returning one — a detail worth getting right up front since a naive `const p2 = Util.applyTransform(p, m)` would silently produce `undefined`) to compute an axis-aligned `PdfRect` bounding box. Deliberately scoped to `paintImageXObject` only, matching the plan's literal step 1 wording — inline images (`paintInlineImageXObject`) and images nested inside Form XObjects are out of scope for this pass, a known narrowing documented in the module's own comment.
- Added `/src/features/workspace/ImageRegionOverlay.tsx`, a read-only sibling to the existing `TextEditOverlay.tsx`: one absolutely-positioned, `pointer-events-none` bordered box per detected region, converting each `PdfRect` to on-screen pixels via the same `viewport.convertToViewportPoint`/`displayScale` mechanism `TextEditOverlay` already uses, with a small numbered label ("Image 1", "Image 2", …) so multiple detections on one page are individually identifiable in a screenshot.
- Wired both into `/src/features/workspace/PagePreview.tsx`: a new "Show images"/"Hide images" toggle button (styled in emerald, next to the existing blue "Edit text" toggle), state reset on page change exactly like `isEditingText` already was, and a `useEffect` that fetches image regions only while the toggle is active — the same shape as the existing text-block-fetching effect.

### Why

Keeping this step strictly detection-plus-static-overlay, with zero interactivity, is what the plan itself asks for: `getOperatorList()`-based detection is a genuinely unproven mechanic in this codebase (unlike Phase 7's text-block clustering, which had at least pdf.js's well-documented `getTextContent()` to build on), so the cheapest way to find out if the coordinate math is even right is to draw the answer on screen and look at it, before investing in drag-and-drop/resize interaction logic that would be built on top of a possibly-wrong foundation.

### What worked

- `tsc -b` and `eslint .` both passed cleanly on the first attempt — reading pdf.js's actual `.d.ts` and runtime source before writing `imageRegions.ts` meant there were no type-shape surprises (unlike, per Step 7's diary, discovering mid-implementation that `TextItem` isn't exported by name).
- Verification went well beyond a visual glance, and was essential given the plan's own framing of this as the phase's riskiest part. I hand-built three synthetic PDF fixtures with Python (raw PDF byte assembly plus PIL-generated JPEGs, the same "hand-write a minimal valid PDF" technique earlier diary entries used for text fixtures) rather than relying on any real-world sample, specifically to control the exact expected answer:
  - **Fixture 1** (`image-sample.pdf`, one 400×300 page): one image nested two `q`/`Q` levels deep, with an outer `1 0 0 1 20 20 cm` translate and an inner `150 0 0 100 80 55 cm` scale-and-position. I hand-computed the expected result via the same matrix composition the code uses (outer-then-inner) to get an expected page-space box of x:100-250, y:75-175 — and the running app's overlay, measured via Playwright's `boundingBox()` on both the canvas and the overlay `div`, produced relative coordinates (`relLeft: 0.25, relTop: 0.41667, relWidth: 0.375, relHeight: 0.33333`) that matched the hand-derived fractions (`100/400=0.25`, `(300-175)/300=0.41667`, `150/400=0.375`, `100/300=0.33333`) exactly.
  - **Fixture 2** (`image-sample-2.pdf`, one 500×350 page): two images, one placed via a single top-level `save`/`cm`/`Do`/`restore`, the second nested two levels deep with an *unrelated* intervening `save`/`cm`(0.5 scale)/stroke-a-rectangle/`restore` sitting between the outer translate and the second image's own inner save — specifically to prove that an unrelated, non-image operator sequence inside a sibling `save`/`restore` doesn't leak into or corrupt the matrix stack state used for the next image. Both detected boxes matched their independently hand-computed expected fractions to within floating-point/sub-pixel rounding (e.g. `relLeft: 0.05998...` vs. expected `0.06`).
  - **Fixture 3**: re-used fixture 1, but rotated the page 90° via the existing rotate button before toggling "Show images" — confirming the overlay still lines up with the visually-rotated image, since detection operates in unrotated PDF space and both the canvas render and the overlay's coordinate conversion go through the same rotation-aware `getPageViewport` transform.
  - All three were driven with a real headless Chromium via Playwright (installed into a scratch npm project under this job's tmp directory, following the pattern established in every prior phase's diary entry), and the final screenshots were visually inspected, not just numerically compared — both checks agreed.

### What didn't work

Nothing failed outright this step — no incorrect intermediate attempt, no typecheck/lint error, no hung Playwright call. The only real friction was procedural rather than a bug: my first Playwright script computed the overlay's position relative to `page.locator('canvas').first()`, which matched the small thumbnail-grid canvas (earlier in DOM order) rather than the larger preview-panel canvas the overlay is actually positioned against, producing nonsensical relative coordinates like `relLeft: 7.9` (physically impossible for a box that's supposed to be within its container). Recognizing that a ratio greater than 1 or wildly off from a sane 0-1 range means "wrong reference element," not "wrong math," and fixing the selector to target `canvas.max-h-\\[75vh\\]` (the preview panel's own distinguishing class) resolved it immediately, after which the numbers lined up exactly.

### What I learned

Deriving the fixtures' expected bounding boxes by hand, via the *same* matrix-composition formula the implementation uses, and then checking the app's actual output against that derivation, is a stronger verification than it might first appear — it's not just "does a box appear roughly over the image," it's "does the box's position match a specific number computed independently, via nested transforms deliberately chosen to be non-trivial (an outer translate composed with an inner scale-and-translate, not just a single flat `cm`)." A bug in composition order (e.g. multiplying the matrices in the wrong sequence) would very likely still produce *a* box roughly near the image for simple single-level cases, but would diverge from the hand-computed fraction the moment two non-commuting transforms are nested — which is exactly why the deliberately-nested fixture, not just a flat one, mattered here, echoing the project's now-repeated lesson (Step 3's square-page rotation trap, Step 7's one-line-tall block trap) that the easy, obvious test case often can't distinguish a working implementation from a subtly broken one.

### What was tricky

The only real subtlety was `Util.applyTransform`'s in-place mutation signature (`static applyTransform(p, m, pos = 0): void`) rather than a pure function returning a new point — easy to miss since its name reads like it should return the transformed point, and pdf.js's own typings (`p: any`) give no hint that it's a mutation. Catching this by reading the actual runtime source before writing code, rather than discovering an `undefined` bug at runtime, was worth the extra few minutes.

### What warrants review

- `/src/lib/imageRegions.ts`'s scope is deliberately narrow, matching the plan's own step-1 wording: only `OPS.paintImageXObject` is detected. Real-world PDFs using inline images (`paintInlineImageXObject`, common for small/simple raster content some PDF producers inline directly rather than as a separate XObject) or images placed inside a Form XObject (a nested, reusable content stream — pdf.js's flat `getOperatorList()` on the *page* does not recurse into these automatically) would silently show zero detected images, or fewer than actually present. This wasn't tested against any real-world-authored PDF (only the three hand-built synthetic fixtures above), so its accuracy on genuinely varied, non-synthetic documents — different PDF producers, embedded scanned pages, PDFs with images inside forms/annotations — is unverified and should be tried against real samples before Step 2 assumes this detection is complete.
- The "Show images" toggle in `/src/features/workspace/PagePreview.tsx` and the "Edit text" toggle are independent and can both be active simultaneously — this wasn't restricted, since the image overlay is entirely `pointer-events-none` and so cannot interfere with the text overlay's `contentEditable` boxes, but it's a deliberate non-decision worth a second look once Step 2 makes the image overlay interactive (draggable), at which point having both editing modes active together may need reconciling.
